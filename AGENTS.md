# Правила разработки dbook

Инструкции действуют для всего репозитория. Перед изменениями изучайте затрагиваемый код и сохраняйте существующие пользовательские изменения. Выполняйте задачу в текущем checkout; не создавайте Git worktree без явного запроса.

## Стек и устройство проекта

- Java 21 (нужен JDK с `javac`), Spring Boot 4.1.1, Maven Wrapper 3.9.16.
- Spring MVC, Spring Security, Spring Data JPA, PostgreSQL 16, Liquibase, JJWT 0.12.6.
- Один Maven-модуль; основной пакет — `ru.dbook.booking`, точка входа — `BookingApplication`.
- Код приложения: `src/main/java`; конфигурация и миграции: `src/main/resources`; тесты: `src/test/java`.
- Используйте `jakarta.*` для Persistence и Validation. Не добавляйте другой фреймворк, Lombok или слой абстракций без необходимости для задачи. Версии управляемых зависимостей оставляйте Spring Boot.

## Границы слоёв

- `controllers`: HTTP-маршрутизация, `@Valid`, вызов сервиса, HTTP-статус и DTO ответа. Бизнес-логику и обращения к репозиториям размещайте в сервисах.
- `service`: бизнес-правила, координация репозиториев, транзакции и получение текущего пользователя. Записывающие операции оформляйте `@Transactional`, читающие — `@Transactional(readOnly = true)`.
- `repository`: интерфейсы `JpaRepository`, производные методы и явные JPQL-запросы для доступа к данным.
- `entity`: JPA-модель с конструктором без аргументов; существующие связи бронирований загружаются лениво. Не отдавайте сущности напрямую через API.
- `dto`: Java records для запросов и ответов; преобразование сущностей в ответы следует существующим статическим методам `from(...)`. Выполняйте преобразование внутри сервисной транзакции, если нужны ленивые связи.
- `exception`: предметные исключения и централизованный `GlobalExceptionHandler`.
- `config` и `security`: конфигурация Spring и обработка JWT. Сохраняйте внедрение зависимостей через конструктор и `final`-поля; не переносите статическое хранение зависимостей из `TestController` в новый код.

## HTTP API и ошибки

- Базовые пути храните в `enums/Routes`; существующий API использует `/api/v1`. Подпути задавайте аннотациями контроллеров.
- Сохраняйте JSON-поля и HTTP-контракты существующих DTO. Входные ограничения задавайте аннотациями Jakarta Validation, бизнес-проверки — в сервисе.
- Успешное создание комнаты, бронирования и регистрация возвращают `201`; чтение, вход и обновление токена — `200`; выход — `204`.
- Добавляя предметное исключение, задавайте соответствующий обработчик: неверные данные — `400`, аутентификация — `401`, запрещённая операция — `403`, отсутствующая комната — `404`, конфликт — `409`.
- Сохраняйте формат ошибки `{"message": "..."}`; ошибки валидации дополнительно содержат `errors` с сообщениями по полям. Не раскрывайте детали внутренних исключений клиенту.
- Имена Java-элементов и сообщения API пишите на английском, согласованно с существующим кодом. Используйте отступы в четыре пробела; избегайте массового переформатирования соседнего кода.

## Аутентификация и права

- Сессии stateless: access token передаётся как `Authorization: Bearer ...`; `JwtAuthenticationFilter` устанавливает аутентификацию до стандартного фильтра логина.
- `/api/v1/auth/**`, `/error` и OPTIONS доступны без аутентификации; остальные маршруты защищены. Сохраняйте правила `SecurityFilterChainConfig` и method security из `SecurityConfig`.
- Комнату создаёт `ADMIN`; бронируют `ADMIN` и `TRAINER`; список активных комнат и собственных бронирований доступен аутентифицированным пользователям. Согласовывайте `@PreAuthorize`, `UserRole.canBookRoom()` и сервисные проверки при изменении прав.
- При регистрации всегда назначается `USER`. Не принимайте роль или владельца бронирования из пользовательского запроса; текущий пользователь определяется через Spring Security.
- Email нормализуется через `toLowerCase(Locale.ROOT)`, пароль хранится через `PasswordEncoder` (BCrypt).
- Сохраняйте проверку срока refresh token и ротацию с удалением старого токена. Не логируйте пароли, JWT, refresh tokens и секреты.

## Правила бронирования

- Бронировать можно только активную комнату; начало не должно быть в прошлом, конец должен быть после начала.
- Длительность — от 15 минут до 12 часов включительно, кратно 15 минутам; минуты начала и конца также кратны 15. Текущая реализация не проверяет нулевые секунды и наносекунды: не считайте такую проверку уже существующей.
- Пересечение определяется как `existing.startsAt < new.endsAt && existing.endsAt > new.startsAt`. Соседние интервалы с общей границей допустимы.
- Текущая проверка пересечения запросом перед сохранением не гарантирует отсутствие гонок при параллельных запросах. Если задача требует конкурентной безопасности, отдельно предусмотрите защиту на уровне БД/блокировок и интеграционную проверку.
- Список комнат содержит только активные комнаты, сортируется по имени; собственные бронирования сортируются по началу.
- Время бронирования представлено `LocalDateTime` / SQL `TIMESTAMP`, время создания — `Instant` / `TIMESTAMPTZ`. Изменение временной модели требует согласованных изменений DTO, сущностей, миграций и тестов.

## База данных и конфигурация

- Источник схемы — `src/main/resources/db/changelog/db.changelog-master.yaml`. Добавляйте новые нумерованные SQL-файлы в `changes/`, с `--liquibase formatted sql`, уникальным changeset и включением в master.
- Уже применённые changesets не переписывайте. Изменения сущностей сопровождайте миграциями, включая необходимые ограничения и индексы.
- Проверяйте совместимость на PostgreSQL; не подменяйте его H2 при проверке SQL, миграций и поведения репозиториев.
- В `application.yaml` установлено `ddl-auto: validate`. Compose по умолчанию переопределяет его на `update`; для проверки миграций явно задавайте `SPRING_JPA_HIBERNATE_DDL_AUTO=validate`.
- Передавайте настройки через переменные окружения. Для JVM на хосте нужен `SPRING_DATASOURCE_URL=jdbc:postgresql://localhost:5432/dbook`; имя `db` из штатного YAML доступно внутри сети Compose.
- `.env` игнорируется Git. Не коммитьте реальные пароли и JWT-секреты; значения из примеров не используйте как рабочие секреты. Spring сам по себе не загружает Compose `.env`.

## Запуск и проверка

Все команды проекта выполняются из корня репозитория.

1. Проверьте `java -version` и `javac -version`: оба должны соответствовать Java 21. Используйте `./mvnw`, чтобы соблюдать версию Maven из wrapper.
2. Для PostgreSQL задайте `POSTGRES_PASSWORD` в локальном `.env` или окружении и выполните `docker compose up -d db`. Дождитесь `docker compose exec -T db pg_isready -U dbook -d dbook` (при изменённых имени БД/пользователе подставьте свои значения).
3. Для запуска JVM на хосте задайте `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD` и `SECURITY_JWT_SECRET`. Пароль должен совпадать с паролем уже инициализированной БД. Смена переменной не меняет пароль в существующем volume.
4. Выполните `./mvnw verify`: компиляция, существующие тесты и сборка JAR. Для запуска используйте `./mvnw spring-boot:run`.
5. Для запуска всего стека через Docker используйте `docker compose up -d --build`. Dockerfile пропускает тесты, поэтому успешная сборка образа не заменяет `verify`.

В подготовленной облачной среде доступны необязательные помощники вне репозитория: `/workspace/.dbook-setup/runtime verify` и `/workspace/.dbook-setup/runtime spring-boot:run`. Они настраивают JDK, Maven cache/proxy и локальную БД. Не предполагайте их наличие в другом окружении и не переносите `runtime.env` в Git. Для ограниченной файловой системы выбирайте доступный для записи Maven cache; сохраняйте проверку TLS и checksums.

Единственный существующий тест `BookingApplicationTests.contextLoads` загружает Spring-контекст и требует доступной БД; он не покрывает бизнес-сценарии. Для изменений поведения добавляйте содержательные тесты в соответствующий пакет под `src/test/java`: сервисные правила, HTTP-валидация/права или интеграция с PostgreSQL — по области изменения. Для бронирования проверяйте границы времени, роли и пересечения; для аутентификации — вход, истечение и ротацию токенов.

После изменений запуска приложения проверяйте функциональный запрос: без токена `/api/v1/test` возвращает `401`, регистрация уникального тестового пользователя — `201`, с полученным access token `/api/v1/test` возвращает `200` и `OK`. Не выводите токены в отчёт. Не удаляйте Docker volumes для повторного запуска без явной необходимости и разрешения на потерю данных.

Перед завершением проверьте `git diff --check` и итоговый diff. В отчёте укажите выполненные проверки и фактический результат; отдельно перечислите проверки, которые не удалось выполнить. Для изменений только документации достаточно проверки содержимого и diff, повторная сборка не требуется.
