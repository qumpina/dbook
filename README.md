# dbook — Dance Booking

## О проекте

**dbook** — веб-приложение для бронирования залов танцевальной студии. Оно объединяет каталог помещений, расписание и управление бронями, чтобы тренеры могли резервировать время, а администраторы — контролировать использование залов и предотвращать пересечения.

Система состоит из REST API на Spring Boot, браузерного интерфейса на Vue и базы PostgreSQL. В текущем `master` объединены регистрация и JWT-аутентификация, ролевой доступ, бронирование с миграциями БД, frontend и автоматические проверки. История разработки и результаты саморевью доступны в [отчёте по frontend](docs/reviews/feature-frontend.md).

## Основные возможности

- Регистрация, вход, восстановление сессии после перезагрузки и выход из аккаунта.
- Просмотр активных залов: название, описание и вместимость.
- Выбор зала и даты, подтверждение бронирования и уведомление о конфликте времени.
- Просмотр собственных бронирований и их отмена.
- Профиль с именем, email и ролью пользователя.
- Расписание тренера и общий список бронирований для администратора.
- Административная страница с созданием залов, таблицей броней и счётчиками активных залов и бронирований.

Интерфейс учитывает роль пользователя; права дополнительно проверяются на сервере.

## Бизнес-логика

### Участники и права

| Роль | Возможности |
| --- | --- |
| `USER` | Просмотр залов, профиля и собственных броней; отмена собственной брони |
| `TRAINER` | Возможности пользователя, создание броней от своего имени и просмотр своего расписания |
| `ADMIN` | Создание залов, бронирование, просмотр всех броней и отмена любой брони; через API может указать другого владельца брони |

Регистрация всегда назначает `USER`. Назначения ролей через API или интерфейс нет. Поле другого владельца бронирования доступно администратору в API, но не вынесено в форму frontend.

### Сущности и сценарий бронирования

**User** хранит данные аккаунта, хеш пароля и роль. **Room** описывает зал, вместимость и признак активности. **Booking** связывает один зал с одним пользователем и интервалом времени. У пользователя и зала может быть несколько бронирований. **RefreshToken** связан с пользователем и обеспечивает обновление сессии.

При создании брони сервер определяет пользователя по аутентификации, проверяет его права, активность зала и допустимость интервала. Затем проверяет пересечения и сохраняет запись. Проверка и запись выполняются в одной транзакции с блокировкой строки зала, чтобы два конкурентных запроса не заняли один интервал.

Правила бронирования:

- Начало не должно быть в прошлом, конец должен быть позже начала.
- Бронь целиком находится в одном календарном дне, с **08:00 до 22:00 по Москве** (`Europe/Moscow`).
- Длительность — от **15 минут до 12 часов** включительно, кратно 15 минутам.
- Минуты начала и конца кратны 15; секунды и наносекунды равны нулю.
- Интервалы одного зала не пересекаются. Соседние брони с общей границей допустимы.
- Отменить бронь может её владелец или администратор. Отмена удаляет запись из БД.

Вместимость — характеристика зала: учёт участников занятия и распределение отдельных мест не реализованы. Время начала и конца хранится как `LocalDateTime` / SQL `TIMESTAMP` и трактуется по Москве; время создания записей хранится как `Instant` / `TIMESTAMPTZ`.

### Вход и сессия

Email при регистрации и входе приводится к нижнему регистру. Пароли хешируются BCrypt; при регистрации требуется минимум 6 символов, а максимальная длина ограничена 72 байтами UTF-8.

При входе или регистрации API возвращает профиль, access JWT и refresh token. Access token передаётся в `Authorization: Bearer …`; refresh token хранится в БД и при обновлении заменяется новым. По умолчанию сроки действия составляют 15 минут и 30 дней соответственно и настраиваются через окружение. Frontend хранит токены в `localStorage`, восстанавливает сессию и автоматически обновляет access token. Выход удаляет refresh token и локальную сессию; уже выданный access JWT сохраняет действие до истечения своего срока.

### Границы текущего интерфейса

Форма бронирования предлагает **часовые слоты**, хотя API принимает интервалы с шагом 15 минут. На странице залов отмечаются собственные брони; общего обезличенного календаря чужой занятости API не предоставляет. Конфликт с чужой бронью выявляется сервером при подтверждении. Тренер видит своё расписание, администратор — общее. Редактирование и удаление залов, восстановление пароля и подтверждение email не реализованы.

## Архитектура проекта

Backend — одно Spring Boot-приложение в пакете `ru.dbook.booking`. Frontend — отдельное SPA, обращающееся к API с префиксом `/api/v1`.

```text
Vue views → Pinia / Axios → REST-контроллеры → сервисы → JPA-репозитории → PostgreSQL
                              ↑                 ↓
                        Spring Security     DTO ответов
```

- **Контроллеры** принимают и валидируют DTO, вызывают сервисы и формируют HTTP-ответы. `AuthController` обслуживает `/auth/*`, `RoomController` — `/rooms`, `BookingController` — `/bookings`.
- **Сервисы** реализуют сценарии: `AuthService` координирует вход и регистрацию, `JwtService` работает с JWT, `RefreshTokenService` — с обновлением сессии, `RoomBookingService` — с залами и бронями.
- **Репозитории и сущности** отвечают за хранение и запросы. JPA-сущности преобразуются в DTO перед возвратом клиенту.
- **Security и обработка ошибок** проверяют JWT и права методов, возвращают ошибки валидации, доступа и конфликтов в JSON.
- **Liquibase** применяет версионированную SQL-схему при старте. Миграции также содержат начальные залы и пользователей разных ролей.
- **Frontend** разделён на страницы, layouts, API-клиент, хранилище сессии и маршрутизатор. Защищённые маршруты ждут восстановления сессии; календарь использует общие функции московского времени.

## Запуск проекта

Команды ниже рассчитаны на Bash и выполняются из корня репозитория, если не указано иное. Нужен доступ к реестрам зависимостей и Docker-образов.

### Зависимости и окружение

Для основного варианта нужны **Docker с Compose v2**, **Node.js 24** и npm. JDK 21 нужен при запуске backend вне Docker и для Maven-проверок; отдельно устанавливать Maven не требуется — используется `./mvnw`.

```bash
git clone https://github.com/qumpina/dbook.git
cd dbook
git switch master
cp .env.example .env
```

В локальном `.env` задайте собственные `POSTGRES_PASSWORD` и `JWT_SECRET`, заменив значения шаблона. Для JWT нужен случайный секрет не короче 32 ASCII-символов. `.env` исключён из Git; рабочие значения в репозиторий не добавляются.

| Переменные для Compose | Назначение |
| --- | --- |
| `POSTGRES_DB`, `POSTGRES_USER` | Имя БД и пользователь; по умолчанию оба `dbook` |
| `POSTGRES_PASSWORD` | Обязательный пароль БД |
| `JWT_SECRET` | Секрет подписи JWT; задайте свой |
| `JWT_ACCESS_TOKEN_EXPIRATION_MINUTES` | Время жизни access token в минутах |
| `JWT_REFRESH_TOKEN_EXPIRATION_DAYS` | Время жизни refresh token в днях |

### Backend и PostgreSQL в Docker

```bash
SPRING_JPA_HIBERNATE_DDL_AUTO=validate docker compose up -d --build
docker compose logs -f app
```

Дождитесь сообщения `Started BookingApplication`; выход из просмотра логов через Ctrl+C не останавливает контейнеры. API слушает порт **8080**, PostgreSQL — **5432**. Порты должны быть свободны.

Команда явно включает проверку схемы Hibernate: в `application.yaml` уже задано `validate`, но Compose без переопределения использует `update`. Схему создаёт Liquibase. Пароль в существующем volume PostgreSQL не меняется простой правкой `.env`.

### Frontend

В другом терминале:

```bash
cd frontend
npm ci
npm run dev
```

Откройте адрес, который напечатает Vite; стандартный порт — **5173**, начальная страница входа — `/login`. Браузер обращается к `/api/v1`, а Vite проксирует `/api` на backend `http://localhost:8080`. Дополнительный frontend `.env` для такого запуска не нужен. Для другого адреса backend задайте `API_PROXY_TARGET`; подробности — в [инструкции frontend](frontend/README.md).

Для первого входа можно использовать предзаполненные демонстрационные аккаунты из [миграции пользователей](src/main/resources/db/changelog/changes/001_create_users.sql). Их общий исходный пароль — **`password123`**. Эти аккаунты предназначены для локального знакомства с приложением; перед использованием системы с рабочими данными смените их пароли либо удалите демонстрационные записи.

Также можно зарегистрировать собственный аккаунт: он получит `USER`. Для локальной проверки сценариев тренера и администратора роль своей тестовой записи нужно назначить непосредственно в БД. Это ручная подготовка окружения, а не функция приложения.

### Backend без Docker

Вместо контейнера `app` можно запустить JVM на хосте. В этом варианте PostgreSQL остаётся в Docker, порт 8080 должен быть свободен. После подготовки `.env`:

```bash
docker compose stop app
docker compose up -d db
docker compose exec -T db pg_isready -U dbook -d dbook
```

Дождитесь готовности БД. Команда проверки предполагает стандартные имя БД и пользователя. В Bash загрузите свой `.env` и запустите приложение:

```bash
set -a
source .env
set +a
export SPRING_DATASOURCE_URL="jdbc:postgresql://localhost:5432/${POSTGRES_DB:-dbook}"
export SPRING_DATASOURCE_USERNAME="${POSTGRES_USER:-dbook}"
export SPRING_DATASOURCE_PASSWORD="$POSTGRES_PASSWORD"
export SECURITY_JWT_SECRET="$JWT_SECRET"
export SECURITY_JWT_ACCESS_TOKEN_EXPIRATION_MINUTES="${JWT_ACCESS_TOKEN_EXPIRATION_MINUTES:-15}"
export SECURITY_JWT_REFRESH_TOKEN_EXPIRATION_DAYS="${JWT_REFRESH_TOKEN_EXPIRATION_DAYS:-30}"
./mvnw spring-boot:run
```

Для `source` значения в `.env` должны соответствовать синтаксису Bash: строки со специальными символами заключайте в кавычки. Spring Boot сам по себе Compose-файл `.env` не загружает; внутри Docker имя БД-хоста — `db`, а с хоста используется `localhost`.

### Проверки и сборка

При доступной PostgreSQL и настроенных `SPRING_DATASOURCE_*`, `SECURITY_JWT_SECRET` из предыдущего подраздела:

```bash
./mvnw verify
```

Команда выполняет backend-тесты и создаёт JAR в `target/`. Интеграционные тесты используют настоящую PostgreSQL и проверяют права, временные границы, отмену, JWT и конкурентные запросы. Dockerfile собирает backend с пропуском тестов, поэтому сборка образа не заменяет `verify`.

Из `frontend`:

```bash
npm test
npm run lint
npm run build
```

Для браузерных проверок backend должен работать. Playwright сам запускает Vite и проверяет сценарии в UTC и America/Los_Angeles:

```bash
npx playwright install chromium
npm run test:e2e
```

Используйте отдельную БД для разработки и тестов: браузерные сценарии создают аккаунты. Workflow [Verify application](.github/workflows/verify.yml) выполняет backend- и frontend-проверки, `npm audit` и Playwright для PR в `master`, а также push в `master` и `feature/frontend`.

### Остановка и размещение сборки

`docker compose down` останавливает Docker-стек, сохраняя данные в volume. Frontend останавливается через Ctrl+C в его терминале.

Compose и корневой Dockerfile обслуживают только backend и БД. Frontend собирается отдельно в `frontend/dist/`; для его размещения нужен веб-сервер с перенаправлением неизвестных SPA-маршрутов на `index.html` и reverse proxy `/api` на backend. Готового production-развёртывания всего стека в репозитории нет.
